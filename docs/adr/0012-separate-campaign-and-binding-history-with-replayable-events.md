# Separate Campaign and Binding history with replayable Events

Status: accepted and persistence-proven by Wayfinder #18. The SQLite prototype validated atomic accepted mutations, revision reconstruction, forks, stale tabs, migration, backup/restore, and restart behavior; #26 will confirm or revise the final architecture from measured evidence.

Campaign truth and chat-specific state use separate optimistic-concurrency histories inside one SQLite authority. Every accepted Campaign Operation creates exactly one Campaign Revision and immutable Campaign Event; every accepted Binding Operation creates one Binding Revision and immutable Binding Event without manufacturing a Campaign change. Binding identity, Campaign Anchor, Sync Boundary, and Context pins use fixed facet counters so unrelated chat-specific actions do not conflict, while one transaction may append both Event kinds for explicit campaign-and-anchor or branch-and-bind workflows.

Campaign Events retain schema-versioned normalized before/after subject images behind a hash chain. A self-contained revision-zero Campaign Base, rebuildable current projections, and periodic snapshots allow deterministic numbered-revision reads and independent branches without replaying old validation code or depending on a parent Campaign. A globally ordered durable invalidation feed indexes accepted transactions but never carries canonical client state.

This rejects one shared revision counter, current-state-only storage, temporal version tables for every subject, automatic binding advancement, locator-only binding lookup, and copy-on-write branches. The extra Event/replay machinery is justified by arbitrary reconstruction, idempotent multi-tab writes, explicit copied-chat recovery, safe Delete with intact history, and deterministic backup recovery. Detailed Interfaces and retention rules are recorded in [Campaign authority, history, and Chat Binding lifecycle](../design/campaign-authority-history-and-bindings.md).
